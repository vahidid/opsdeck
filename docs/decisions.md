# Decisions

## Made

| # | Decision | Why |
|---|---|---|
| 1 | Local-first; no cloud dependency | Requirement |
| 2 | Core runs as a daemon; CLI/UI/MCP/AI are clients | Shared unlocked vault, tunnels, sessions, one audit trail |
| 3 | Workspace files contain no secrets, only `vault://` references | Git-friendly, shareable |
| 4 | Key hierarchy: password → KEK → Vault Key → per-scope keys | Password change, multiple unlock methods, per-project isolation |
| 5 | Argon2id + XChaCha20-Poly1305 | Modern, well-reviewed defaults |
| 6 | "Use vs reveal" split; agents can never reveal | Lets AI operate without seeing secrets |
| 7 | Per-workspace known_hosts (TOFU) and credentials; per-workspace `ssh-agent` socket for external tools is designed but **not built yet** | Isolation, works with existing tools |
| 8 | Resource envelope (`kind/name/via/spec`) + providers | Add VPN/Docker/K8s/logs later without changing the core |
| 9 | Product is an **agent harness** (like Claude Code / opencode) focused on infra; the web UI is the first client (a TUI can follow on the same API) | Requirement |
| 10 | Everything the agent can do, the human can do from the UI (terminal, exec, files, docker, k8s, logs); CLI subcommands per tool are **not built yet** | "Usable without AI" |
| 11 | Safety before execution: risk classes × environment policy, plan mode, diffs + backups, one approval listing every host for fan-out (canary rollout **not built yet**) | Infra has no undo |
| 12 | Redaction of every model input + optional local-only models per workspace | Secrets never reach the model |
| 13 | Own harness, not a plugin on opencode/Claude Code; ship an MCP server for interop | Guarantees must live inside the loop |
| 14 | Go backend; React UI embedded in the single binary and served on 127.0.0.1 | One binary per OS, infra libraries are Go-native; UI works everywhere and can be wrapped as a desktop app later |
| 15 | Anthropic via the official Go SDK (streaming, adaptive thinking, effort, server-side refusal fallback); everything else via the OpenAI-compatible protocol | One code path for Claude features, broad coverage for local/other models |
| 16 | Workspace MCP servers require local trust | A cloned workspace must not be able to run commands on this machine |
| 17 | Git credentials reach `git` through stdin/env, never the command line or `.git/config` | The agent can deploy from private repos without seeing tokens |
| 18 | The agent can work on this computer (files, commands, key import) behind consent: reads outside the workspace ask per folder, credential files per file, writes and commands in Ask mode (see 36 for Auto and Full); opsdeck's own files are unreachable | Real tasks start from the user's machine (`~/.ssh`, project folders); a harness that cannot see them is not useful |
| 20 | VPNs are drivers with two modes: userspace (netstack in opsdeck or a SOCKS helper; default) and system (TUN). Native Go where a maintained library exists (WireGuard, tsnet, NetBird embed), official binaries otherwise (openvpn + management interface, openconnect, openfortivpn) | Userspace needs no root and lets many VPNs coexist; system mode is still there when every app must use the VPN. No reliable pure-Go OpenVPN/AnyConnect client exists |
| 21 | The agent may connect userspace VPNs without asking; system-mode connects and all disconnects need approval | A userspace tunnel only affects opsdeck (like an SSH connection); a system tunnel changes the machine |
| 22 | VPN SSO is done by opsdeck (aggregate-auth XML with STRAP/HPKE, GlobalProtect prelogin, FortiGate SAML) with a DevTools-driven browser window or the default browser; the VPN client only receives the resulting cookie | The CLIs need a webview for most SAML flows; doing the exchange ourselves works without IPv6 or an HPKE-enabled openconnect and lets a per-profile browser profile remember the IdP login |
| 23 | Workspace tabs keep every open page mounted (hidden) with its own router location; polling pauses in background tabs; the terminal stays a single tab | Switching tabs must not lose an agent stream, a draft or a log view |
| 24 | Text direction is decided per message (RTL when right-to-left script dominates the prose) and per paragraph otherwise; code is always LTR; Vazirmatn is bundled | Persian answers mix Persian prose with commands and paths |
| 25 | Git working copies live in the workspace (`repos/<name>`, git-ignored) and are driven with the system `git` under an isolated config; credentials are an origin-scoped header or an in-memory ssh-agent; `via` goes through a per-command authenticated local SOCKS proxy | Same behaviour as the user's own git (protocols, LFS-free repos, SSH), no secret on disk or in argv, and no user/system git config (helpers, hooks, aliases) can interfere |
| 26 | Local repository edits and commits need one approval per repository per session; pushing asks with the outgoing diff, pushing to default/protected branches and merging always ask | Nothing leaves the machine before a push, so editing should be smooth; the push and the merge are what reach infrastructure |
| 27 | Git accounts are connectors on this computer (not per workspace); workspaces only reference a connector and a URL, and a repository without one uses the connector of its URL's server | Signing in once per account matches how people use GitHub/GitLab; workspace files stay shareable (no account details) and adding a repository becomes picking it from a list |
| 28 | The topology is a separate, hand-and-agent-edited model (`topology.yaml`) rather than derived from the inventory; the inventory can be imported into it | Most of what matters (CDN, WAF, routers, what runs where, which protocol) is not an SSH target; the map must describe it anyway |
| 29 | Agent changes to the topology always ask (also in Auto mode; not in Full, see 36), with a diff; one "always" per session | The map is shared documentation the user relies on; the agent proposes, the user decides |
| 30 | A built-in skill library (MIT, from wshobson/agents, unchanged and attributed) ships in the binary; workspaces can turn it off or override a skill by name | Good procedures out of the box without copying files into every workspace |
| 31 | The topology map is laid out with ELK (elkjs, EPL-2.0, loaded only on the topology page) and connections are routed by our own orthogonal router around the components; the layout is still stored per component in `topology.yaml` | A layered layout puts the internet at the top and data at the bottom and keeps zones nested; an obstacle-aware router is what keeps a dense map readable, and no maintained JS router does this in the browser (libavoid needs WASM) |
| 32 | Scripts are a separate object from skills: code that runs as one unit with typed parameters, in a personal library (every workspace) and per workspace (shared through git; a workspace script wins by name). They are approved by content hash; anything the agent or an outside edit changes becomes a draft, and drafts always ask and never run on protected environments. Secrets travel over stdin into a private temporary folder | A skill is followed with judgment and can differ every time; a bootstrap must run exactly as reviewed. A DevOps engineer's toolkit spans customers, while a project's scripts must be reproducible for the team |
| 33 | Docker stays CLI-over-SSH (no socket forwarding, no agent on the host). Volume files are reached directly, with `sudo -n`, or through a throwaway helper container, by a script that confines every path to the volume; logs keep stdout/stderr apart over the SSH channels and carry docker's timestamps so a dropped stream resumes with `--since` | Works on any host the user can SSH into, with the permissions they already have; nothing to install or expose. Volumes live under root-owned paths, and the helper container covers hosts without sudo |
| 34 | Kubernetes goes straight to the API with client-go: tables come from the server-side Table API (the columns `kubectl get` prints, for CRDs too), changes are server-side apply with the field manager `opsdeck` and a dry run for the diff, and a cluster with `via` is reached through an authenticated local SOCKS proxy (set as the client's proxy, so exec, logs and port-forward upgrades use it too) | No `kubectl`/`helm` to install or keep in step with the cluster; any resource type works without per-kind code; the dry-run diff includes defaults and admission webhooks; a custom dialer is ignored by client-go's upgrade transports, a proxy is not |
| 35 | Ansible runs on this computer with the user's own ansible; Ansible Vault is implemented natively. Vault passwords are typed when needed and kept in memory (or saved in the vault on request); the agent gets them only through a password field on its approval card, and they reach ansible as `--vault-id` files in a private temporary folder | No extra runtime to ship, and the ansible version the team already uses; viewing and editing vault files work without ansible and without writing the password anywhere. The password is the user's to give: a card per action (or per session) keeps that explicit while letting the agent do the work |
| 36 | Modes are split by scope: Auto runs everything on this computer except destructive commands, credential files and vault/topology changes; Full runs everything on this computer; changes on servers ask in every mode unless the user turns that off in App settings | The user's own machine is where an agent harness has to move fast, as in a coding harness; production servers have no undo, so the default keeps a person on every server change whatever the mode |
| 37 | Knowledge is pushed, not only offered: a local BM25 index (with a Persian→English vocabulary) over skills, docs, reports, memory and scripts is searched for every user message, and good matches are attached to that message (a clear-best workspace skill in full); a `knowledge` tool searches it on demand | Models skip long lists of skill names; a local search costs milliseconds and no tokens, finds the team's own procedures for Persian requests too, and keeps the system prompt stable for caching |
| 38 | Consecutive tool calls are shown as one collapsible group with a summary (tools ×n, waiting, failed, time) | Long investigations buried the conversation; grouping hides nothing — every call opens with its full input, output and approval |
| 39 | Web access is built in (search, read pages, end-of-life and vulnerability lookups) behind an SSRF-guarded client: every URL, redirect and resolved IP must be public, sites outside an allowed list ask once, pages are wrapped as untrusted, and the next change after web content asks in every mode | Vendor docs, release notes and CVEs are half of operations work; a page is attacker-controlled text that must neither reach internal addresses (opsdeck itself, cloud metadata) nor steer the agent into a change unnoticed |
| 40 | Workspace APIs (panels, Prometheus, Loki, Elasticsearch) get their own tools that go through the workspace's paths and vault logins, separate from the web tools | The same HTTP call is a public read in one case and an authenticated call into private infrastructure in the other; keeping them apart keeps the SSRF guard strict and the credentials out of the model |
| 41 | Allowed reads of one model step run in parallel (bounded); changes stay serial and in order, each with its own approval | Investigations fan out over many hosts and APIs; ordering only matters for what changes things |
| 42 | Subagents run inside opsdeck's own loop with their own context and tool set; read-only subagents run in Plan mode, and their events belong to the session (nested under the delegate call) | Parallel investigations without filling the main context, while every call still goes through the same policy, approvals, redaction and audit |
| 43 | Hooks are commands on this computer with the event as JSON on stdin (Claude Code's model); App settings hooks may also allow a call, workspace hooks can only block or ask and run only after the user trusts them on this machine | A familiar, language-agnostic extension point; a cloned workspace must not be able to run commands or loosen approvals by itself |
| 44 | Background tasks notify the session and an idle session starts a turn by itself; a canary rollout is one call with a second approval after the first host | Long work should not hold a turn open; a rollout should be stoppable after one host without the agent having to plan it as separate calls |
| 45 | `opsdeck run` is a client of the running opsdeck (same login token) and its sessions are headless: anything that would ask is denied | One place for vault, VPNs and policy; a job never hangs waiting for an approval nobody will give, and what it may do is stated explicitly in rules or the mode |
| 46 | DNS / CDN providers (Cloudflare, ArvanCloud) are connectors on this computer like Git accounts; a workspace `Domain` holds only the zone (and optionally the connector), and records are shown and edited in one provider-neutral shape (relative name, text content, TTL, priority, proxied) that each provider maps to its own API; the agent's `set`/`delete` fetch the record first so the approval card shows before and after | The same "connect once, pick from a list" flow as repositories, shareable workspace files, and one Domains page and one tool whatever the provider; a DNS change is cheap to make and slow to undo, so the user must see exactly which line changes |
| 47 | Certificates are ACME with dns-01 only, solved through the DNS connectors; the certificate and key are a vault item of the workspace (readable metadata fields next to the secret key), the ACME account key another; deployment copies files to hosts from the vault, and automatic renewal only renews into the vault (deploying stays a visible step) | dns-01 needs no reachable web server and covers wildcards and internal hosts; the vault is already the place the agent can use but not read, so the key never enters a model context; a renewed certificate that silently replaced files on production servers would bypass the approval model |
| 19 | Secrets move from local files into the vault inside opsdeck (`vault_import_ssh_key`, `vault_add_item` with `file`/`generate`), never through the model | Keeps "secrets never reach the model" while letting the agent onboard credentials |
